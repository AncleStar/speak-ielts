## 4. 技术路线：先验证，再定案

建议候选路线为“本地打包的 React 客户端 + Capacitor iOS 原生能力 + 现有服务端”。这是候选方案，尚未视为已验证的架构。

| 路线 | 适用条件 | 本项目判断 |
| --- | --- | --- |
| React + Capacitor | 希望复用界面和交互，同时接入原生能力 | 优先做登录、录音、回放和磁盘性能小样 |
| React Native | WebView 的录音、交互或性能无法满足要求 | 小样失败后评估；业务接口可保留，界面需要迁移 |
| Swift / SwiftUI | 希望长期以原生 iOS 为主，接受更多界面开发成本 | 保留为后续选择，不在准备阶段重写全部界面 |

Capacitor 需要可构建的客户端静态资源和入口页面，现有带 SSR、Server Actions、数据库及 worker 的 Next.js 工程不能整体原样打包。先梳理前后端依赖，再决定是否建立独立移动客户端目录。[官方安装要求](https://capacitorjs.com/docs/getting-started)

正式客户端使用随安装包交付的界面资源；开发热更新可以使用独立开发配置。Capacitor 的 `server.url` 用于开发热加载，不作为本计划的生产发布方案。[官方配置说明](https://capacitorjs.com/docs/config)

小样通过条件：在实际 iPhone 上完成登录 → 选盘 → 播报 → 录音 → 上传 → 反馈 → 回放 → 退出，并验证中断与跨账号隔离。仅出现可打开的 WebView 不计为通过。

## 6. Windows 上先完成的工程准备

### 6.1 划分可复用代码

- 业务数据类型、题库映射、显示逻辑、日期和费用计算先评估复用。
- 数据库、worker、AI 调用、密钥解密、私有文件访问保留服务端。
- 盘点 `app/actions/`、服务端页面、Node.js 导入，以及当前直接使用 Cookie、DOM、IndexedDB 的代码。
- 音频、网络、会话存储、文件及应用生命周期做适配接口；浏览器实现与原生实现分别验证。
- 现有 Web 工程继续正常运行。移动客户端接入通过可复用服务层承接业务规则，减少双份规则发生偏差。

对应产物见 [架构与迁移清单](ios/架构与迁移清单.md)、[客户端能力与录音规则](ios/客户端能力与录音规则.md) 和 `lib/ios/ports.ts`；原生实现仍待小样。

### 6.2 登录与写入接口是首个技术门槛

现有 `lib/request-origin.ts` 仅接受配置中的 HTTP/HTTPS 来源，写入接口在共享包装层校验 Origin/Referer。移动端本地页面来源、原生网络请求和 Cookie 管理与浏览器不同，直接调用可能被拒绝。

准备工作：

1. 分别绘制 Web Cookie 会话与移动客户端会话的请求过程；明确注册、首次改密、登录、会话失效和退出。
2. 评估现有 Better Auth 的官方 Bearer 能力，先在隔离环境验证与项目锁定版本兼容，再决定是否采用；目前未启用该方案。[Better Auth 官方说明](https://better-auth.com/docs/plugins/bearer)
3. 若采用 Token，会话凭据使用 Keychain 等原生安全存储；定义过期、重新认证、撤销及改密后失效，不假定现成插件包含所有行为。
4. 移动入口按经过验证的凭据、账号权属、授权状态和幂等规则处理；明确 Cookie 与 Token 同时出现时的优先级，禁止歧义身份。
5. 网页端继续保留来源防护。不能通过允许任意 Origin、信任客户端 Host、或全局放行无来源请求来解决移动兼容问题。
6. 新增验证覆盖：伪造来源、空 Token、过期 Token、改密/删除后旧 Token、双账号访问、登录失败限速及退出后的缓存清理。

### 6.3 明确移动 API 契约

拟形成版本化接口契约；是否增加 `/api/mobile/v1` 在架构小样后定案，不预先批量更名现有接口。

| 能力 | 现有入口示例 | 需要写清的规则 |
| --- | --- | --- |
| 用户与配置 | `/api/me`、`/api/ai-settings`、账号 Actions | 原生认证、最小返回字段、账号删除及授权撤回的移动入口 |
| 题库与选盘 | `/api/levels` | 仅返回可用及已审核内容；解锁规则仍由服务端判断 |
| 训练会话 | `/api/sessions` 及其状态接口 | 创建、暂停、结束、模考计时、设备接管与冲突处理 |
| 音频与处理 | 上传凭证、回答提交及重试接口 | 25 MiB 上限、时长核对、授权版本、重复提交与重试 |
| 回放与报告 | 回答音频、参考朗读、报告接口 | 鉴权、Range 回放、删除后的访问失效与缓存清理 |
| 学习与成长 | 观点、词汇、复习、奖励接口 | 编辑冲突、分页、重复操作、时区与账本一致性 |

契约至少包括请求/响应示例、错误码、鉴权、授权条件、幂等键、分页、到期规则及兼容策略。示例只使用虚构账号与合成数据。

## 7. 录音与移动体验准备

### 7.1 先定义录音行为

状态至少包括：等待授权、准备、录音中、正常停止、中断、待上传、上传中、处理中、完成、失败、已撤回。

| 场景 | 预期行为及验证 |
| --- | --- |
| 首次进入 | 先说明用途并完成试音；明确系统麦克风权限与 AI 数据授权是两项不同状态 |
| 拒绝权限 | 提供清楚说明和系统设置入口；允许继续使用可用的文字功能 |
| 来电、锁屏、切后台 | 首版默认停止并保留已完成片段；普通训练提供恢复操作，模考按既定规则中断，不重置原计时 |
| 系统终止 App | 验证实际落盘片段恢复能力；说明最后未完成写入的片段可能丢失，不宣称绝对恢复 |
| 上传时断网 | 保留待上传状态，联网后由用户确认继续；服务端校验不重复创建回答或扣额 |
| 撤回授权、退出或换账号 | 先释放麦克风与播放，再处理本机数据；新账号不能读到旧账号音频或草稿 |
| 蓝牙/有线耳机切换 | 验证音频路由、音量、录音中断和恢复；防止考官播报进入回答录音 |

原生录音候选为 AAC/M4A 或 WAV；具体选择由音质、文件大小、系统接口及服务端实际转码结果决定。后台凭文件内容校验，不能仅相信扩展名或客户端声明时长。

本机未上传录音沿用现有最长 24 小时恢复期限，实际文件与索引需按账号隔离。预先定义导出、清理和撤回授权后的行为，不能直接照搬浏览器 IndexedDB 逻辑。

### 7.2 移动交互与性能

- 明确训练、观点、复习、成长与设置的一级入口；积分兑换、记录和日历保持可发现。
- 核对安全区、键盘遮挡、长文本、横竖屏、动态字体、VoiceOver 和减少动态效果。
- 磁盘仍采用静态圆环；训练和回放保留用户认可的展示方式。
- 原生容器切页后释放录音、播放及 3D 资源；退出面试停止其活动状态。
- 在目标 iPhone 上记录帧时间、内存、发热和页面切换。若 3D 小样不足，准备保留风格的轻量展示；不依据 Windows 视口模拟宣称 iPhone 流畅。
- 手机页面检查可以在 Mac 到位前先用 Safari 建立基线；Safari 通过不能替代原生容器验证。

## 8. 后端、数据与学习质量准备

### 8.1 环境与部署

区分开发环境、隔离试用环境和正式环境。开发环境可使用确定性模拟服务；真实调用沿用预算。客户端内不包含站点密钥、数据库凭据或生产管理员密码。

没有域名/服务器时，可以先制定局域网或临时可信 HTTPS 测试方案。临时地址仅用于隔离试用，不作为 App Store 运行承诺；公开访问不能直接暴露现有私人数据环境。

在 TestFlight 对外试用前落实可访问的 HTTPS 后端。正式发布前完成持久存储、worker 持续运行、异常通知、费用边界、更新与恢复演练。购买 Mac 不会自动完成这些工作；自己的服务器和托管服务都可作为候选，资源购买另行决定。

现有小范围试用可以先使用服务器持久磁盘加独立备份。如果选择 OSS，必须补真实对象访问、删除、备份和恢复验收；OSS 不作为所有部署的强制要求。

### 8.2 内容和反馈

- 首发可见题库及参考表达全部完成人工审核；开启 `CONTENT_REQUIRE_REVIEW=true`，其余内容保持草稿。
- 题目覆盖首版承诺的 Part 1/2/3 和难度范围，人工核对自然表达、题意与参考答案。
- 使用真人的清晰语音、口音、停顿、噪声和静音样本评估；仅使用已同意测试的素材。
- 人工复核至少 30 条反馈：引用用户原话是否准确、纠错是否正确、建议是否重复或空泛。
- 保留“模拟数据”“非官方评分”“发音未评估”等真实能力说明。
- 沿用既有验收目标：20 次完整练习至少成功 19 次，失败可恢复；前台计时/停止误差不超过 1 秒；原速 750 秒模考模板验证。
- 单题反馈 P95 目标不超过 30 秒，整套报告不超过 120 秒。报告同时记录样本量、网络、模型、耗时起止及费用；小样本只标为试测。预算不足时保留未验收状态，不提高预算以完成指标。

| 隐私说明 | 邮箱、录音、文本观点、练习记录、用量等数据的用途、去向、保存和删除规则；申报整条依赖链的实际收集行为 | 外部试用前初稿，提交前核实 |
| 第三方 AI 授权 | 使用前明确告知录音/文本的传输及处理方，并取得相应同意；撤回行为与实际请求一致 | 真实调用前 |
| 账号删除 | 从 App 内可以发起；保留现有后端删除逻辑并补原生退出、凭据和本机文件清理验证 | 外部试用前 |
| 素材及 SDK | 核对模型、字体、头像、音色、贴图及第三方库授权；盘点隐私清单和实际使用的需申报 API | 正式客户端打包前 |
| 地区要求 | 决定发布地区；中国大陆区核实适用的 App/ICP 备案与功能相关资质 | 对应地区正式发布前 |
| 支付策略 | 首版免费无广告；如以后销售额度、题库或会员，按目标商店规则设计内购、恢复购买与用量账本 | 收费功能开发前 |

官方依据：[账号与费用](https://developer.apple.com/programs/enroll/)、[隐私申报](https://developer.apple.com/app-store/app-privacy-details/)、[账号删除](https://developer.apple.com/help/app-review/guideline-reference/5-1-1-account-deletion)、[大陆区信息](https://developer.apple.com/cn/help/app-store-connect/reference/app-information/app-information/)。

审核准备同时核对最低功能、第三方数据共享、登录及支付规则。已有自己的邮箱账号体系，不把新增 Sign in with Apple 当作所有 App 的统一前提；将来增加第三方社交登录时重新核对相关要求。审核展示账号必须能完成训练，个人 API Key 选项的定位与购买引导需要单独核查，不把它作为唯一可体验路径。[App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)

代码的 MIT 许可与第三方素材授权分别登记。保留 RhineLabUI 许可及引用说明，核实实际资源来源；需要替换的资源采用自有或明确获授权的素材，同时保留认可的视觉方向。

## 10. Mac 到位后的本地准备

1. 接入显示器和键鼠，记录 Mac 型号、内存、存储、macOS 版本及可用空间；完成本机备份方案。
2. 按当前官方兼容表安装合适的稳定版 Xcode、Command Line Tools 和 iOS Simulator；锁定版本，不直接沿用文档中的旧版本号。
3. 安装与项目兼容的 Node.js、Git 及原生工程依赖；记录全新安装步骤。需在 Mac 上运行现有后端时另配置 PostgreSQL、FFmpeg 和语音依赖。
4. 创建不带 `.env`、私人录音、数据库和签名凭据的干净源码副本；用虚构用户及模拟服务启动小样。
5. Windows 与 Mac 通过 Git 同步源码或通过局域网编辑；图形调试在 Mac 上进行。签名凭据由本机钥匙串管理，不入 Git。
6. iPhone 与 Xcode 配对，记录开发者模式、设备信任、录音权限、安装及更新步骤。
7. 使用本机 Xcode 做开发签名安装，验证 G1 小样；此阶段的本机安装不等于 App Store 上架。TestFlight 阶段再完成相应会员与分发签名。
8. 留存可复现构建命令、锁文件、版本信息、构建日志及测试结果；构建在自己的 Mac 上执行。

官方依据：[Xcode 系统要求](https://developer.apple.com/xcode/system-requirements)、[Capacitor 环境要求](https://capacitorjs.com/docs/getting-started/environment-setup)、[TestFlight 流程](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview)。

## 11. 三道验收门槛

### G1：可以正式开始 iOS 客户端开发

- [ ] 首版范围、移动导航和录音中断规则明确。
- [ ] 前后端耦合清单、核心接口契约及安全接入方案已形成。
- [ ] 自有 Mac 工具链可复现，实际 iPhone 可安装开发构建。
- [ ] 登录、录音、上传、反馈、回放、退出的小样通过实际 iPhone 验证。
- [ ] 切后台、拒绝权限、断网和跨账号隔离小样有结果及修复方案。
- [ ] 磁盘展示在目标 iPhone 上可用，性能和降级策略有证据。
- [ ] 首批可用测试内容、素材来源及数据授权方案可用于开发验证。
- [ ] 没有遗留会造成越权、密钥暴露、重复扣额或数据丢失的已知 P0 问题。

G1 通过即可展开完整 iOS 开发，公开部署、全量人审和发布材料可按后续阶段继续完成。

### G2：可以邀请用户通过 TestFlight 试用

- [ ] 首版主要流程已在原生客户端实现并验收。
- [ ] 已准备可访问的可信 HTTPS 隔离试用后端和清楚的费用上限。
- [ ] 开发者会员、分发构建、测试资料及可用审核账号准备就绪。
- [ ] 首发可见内容已审核；至少 20 次真人完整练习中成功 19 次，失败可恢复；至少 30 条反馈人工复核有结论，影响核心使用的问题已解决。
- [ ] 原生退出/改密/删除/授权撤回、私有回放、重复提交和失败恢复通过。
- [ ] 设备与网络测试覆盖有明确记录，隐私说明、支持入口与问题反馈可用。

外部 TestFlight 试用可能需要苹果测试版审核；通过时间不作预先承诺。[官方流程](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview)

### G3：可以申请 App Store 正式发布

- [ ] 试用发现的 P0/P1 问题全部关闭；20 次练习和 30 条反馈的门槛有完整记录。
- [ ] 正式服务持续运行、预算限制、独立备份、恢复与升级回滚已验证。
- [ ] 时延、音频、计时、内容和支持的 iOS 版本有对应证据；未达标能力已修复或调整上线范围及说明。
- [ ] 应用签名、隐私清单、第三方依赖、商店截图及介绍与最终构建一致。
- [ ] 地区相关资料、账号删除、数据共享同意、支付及素材许可核对完成。
- [ ] 清洁源码、客户端产物和日志扫描通过，未包含私人资料或服务端密钥。

G3 是内部提交条件，苹果最终审核结果另行记录。

## 12. 测试证据与缺陷管理

| 证据层 | 能证明什么 | 不能代替什么 |
| --- | --- | --- |
| Windows 单元/集成/浏览器测试 | 业务规则和浏览器实现的可复现行为 | 原生容器、真实 iPhone 的录音与后台行为 |
| iOS Simulator | 原生构建、页面及部分交互 | 真实麦克风、音频路由、发热和来电中断 |
| 自有 iPhone 小样 | 该设备及系统上的关键兼容性 | 所有 iPhone 和全部 iOS 版本 |
| 真人及人工审核 | 实际识别和教学质量样本 | 官方雅思评分或普遍学习效果保证 |
| 目标环境运行与恢复 | 该环境的安装、持久化与恢复 | 未验证的其他机器、存储及灾难场景 |

每次记录代码版本、工具版本、设备、系统、网络、配置、服务类型、开始/结束时间、实际结果和问题编号。原始失败和后续复验分别保留。公开报告仅包含脱敏结果，真人录音、凭据和用户信息保存在被 Git 忽略的私人目录。

准备阶段优先测试会话隔离、录音恢复、计费幂等及上传边界。文案和计划文档改动只做格式、引用和发布范围检查，不为文档新增业务测试。

## 14. 计划后的第一轮工作

建议先执行以下可在 Windows 完成的准备包：

1. 建立首版功能矩阵和 iOS 准备任务表，标明现有实现、需要迁移和后续功能。
2. 盘点 Server Actions、Cookie、来源校验、浏览器存储及录音依赖，形成移动端迁移清单。
3. 写出登录、会话、上传、回放、账号删除和费用的最小接口契约与负面测试清单。
4. 定义原生录音的中断、恢复、清理和计时规则，以及移动页面导航。
5. 整理素材授权、首发题库人审和隐私数据流工作表；为 Mac 小样准备无私人信息的测试数据。

第一轮交付应达到：拿到 Mac 后可以按清单安装环境、运行关键小样，并根据真实结果决定是否进入完整 iOS 开发。
