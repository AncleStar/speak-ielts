# 备份恢复与回滚

## 需要保存的三类数据

1. PostgreSQL 数据库：用户、凭证、题库版本、会话、反馈、个人观点、词汇、复习、队列和用量。
2. 私有音频：本地模式的应用 `data/storage` 或 OSS 对象。
3. **最新外部删除日志** `data/deletion-log.jsonl`：恢复较旧数据库后仍要应用的删除意图。不能仅使用旧数据库备份时的日志。

另外独立保管服务端配置、认证密钥与 `USER_API_KEY_SECRET`（若未单独设置，则个人 Key 从认证密钥派生加密）。恢复后更换有效加密密钥会使已保存的个人 Key 无法解密，需要用户重新填写。密钥不要存到公开仓库。备份目录包含个人数据和认证数据库，访问权限应与数据库相同。

## 备份

Docker 的 `backup` 服务每天执行 PostgreSQL 17 `pg_dump --format=custom`，同时打包应用数据；备份文件先写 `.partial`，成功后改名。每天备份保留 7 天，最新删除日志单独保存。迁移前自动运行一次备份。

手动执行一次：

```sh
docker compose run --rm backup-premigrate sh /ops/backup-once.sh manual
```

查看 `backups/` 中成对的 `.dump`、`.data.tar.gz` 以及 `deletion-log.latest.jsonl`。把备份同步到独立介质，不能只依赖同一台主机。备份日志失败时应先排查存储空间、数据库连接和权限，不得把 `.partial` 当成有效备份。

Windows 本机首次运行：

```powershell
npm run setup:backup
npm run backup
```

第一条命令从 PostgreSQL 官方下载页所链接的 EDB 取得 17.10 便携客户端，检查固定 SHA-256，再只提取 `pg_dump`、`pg_restore`、运行库与许可。约 334 MB 的下载只在首次需要，保存在被 Git 忽略的 `data/tools/`，不安装系统服务。Linux/macOS 安装 PostgreSQL 17 客户端，或通过 `PG_DUMP_PATH` / `PG_RESTORE_PATH` 指定现有客户端。

`npm run backup` 现在创建完整目录，默认放在 `data/backups/interview-时间-随机标识/`，也可设置 `BACKUP_DIR`：

```text
manifest.json            # 格式、版本、文件大小与 SHA-256
database.dump            # PostgreSQL custom 格式
deletion-log.jsonl       # 备份时的外部删除意图
storage/                 # 本地录音和考官音频
```

数据库使用导出的同一事务快照。脚本检查该快照引用的未过期录音与就绪考官音频是否已经复制，缺失文件、损坏日志或工具失败都会中止，不发布完整备份目录。`.partial` 不可恢复。运行中的音频清理或转码可能使备份安全失败，应停止正在修改音频的服务后重试。

仅支持本地存储的完整备份；OSS 配置会明确拒绝，而不会把数据库单独备份称为完整备份。不会打包 `.env`、私钥、数据库物理目录、语音模型或运行日志。哈希用于发现文件损坏，不提供来源认证，只恢复自己保存或信任的备份。

本机目录不会自动按天删除。应另行保留多份，并复制到独立介质。服务端配置和加密密钥仍须独立私密保存；仅有数据库与音频不足以恢复个人密钥解密。

## 本机隔离恢复

由 PostgreSQL 管理工具创建新的 PostgreSQL 17 空库，例如 `interview_recovery`（从 `template0` 创建）。保持恢复环境的 web / worker 关闭，保留当前应用库与当前数据目录。

在项目目录的 PowerShell 中设置本次操作使用的环境变量：

```powershell
# 连接值使用自己的本机 PostgreSQL 用户、密码和端口，不要粘贴到聊天或提交到 Git
$env:RESTORE_DATABASE_URL = 'postgres://postgres:YOUR_LOCAL_PASSWORD@127.0.0.1:5433/interview_recovery'
$env:RESTORE_DATA_DIR = './data/restores/recovery-01'
$env:RESTORE_LATEST_DELETION_LOG = './data/deletion-log.jsonl'
npm run restore -- './data/backups/interview-具体备份目录'
```

恢复必须使用不同于当前应用的新库名、无人连接的新空库以及尚不存在的数据目录；不提供覆盖原库选项。恢复前检查目录、文件清单、每个 SHA-256 与数据库 archive，然后复制音频、执行单事务 `pg_restore`、迁移，并合并和重放旧日志与最新日志。会话、账号、个人观点和词汇的删除都支持重放；重复记录合并，冲突和坏 JSON 会中止。

最新日志缺失时默认拒绝恢复。如果部署者确实核对过、确认没有备份之后的删除操作，可设置 `$env:RESTORE_NO_LATER_DELETIONS = 'true'`。这不是找不到日志时的通用绕过办法，旧备份无法推断后来的删除意图。

成功时生成 `restore-complete.json`。恢复的旧登录会话被撤销、未使用邀请码被撤销、进行中面试标为中断；不会自动启动网页或 worker。失败保留 `restore-pending.json` 和独立目录、数据库用于排查，应用环境发现该标记会拒绝提供服务。不要直接移除标记把失败恢复伪装成成功，保留原库并换新空库重新演练。

切换入口前，核对账号与权限、音频回放、观点/词汇/复习、进度及用量；检查备份之后的密码变更和调用费用，必要时由管理员重置密码并对账。较旧备份本身不能包含后来更改的密码或产生的调用。保留原认证/加密配置后，才把恢复环境的 `DATABASE_URL`、`DATA_DIR`、`LOCAL_STORAGE_DIR` 指向新位置，逐项完成冒烟验证。

## Docker / OSS 恢复演练

先在隔离目录和新数据库演练，保持正式 web / worker 关闭。以下顺序不能省略：

1. 选定数据库与对应应用数据包，并保存事故前仍可读取的最新删除日志。
2. 使用 PostgreSQL 17 的 `pg_restore` 恢复到新建空数据库，不覆盖原库。
3. 解压应用数据到新的私有数据目录，或连接隔离的 OSS 恢复桶。
4. 合并恢复包内的日志与最新外部日志；重复记录允许，损坏行应修复后再继续，不能静默跳过。只要最新日志存在，就不能用旧日志覆盖它。
5. 为恢复环境设置 `DATABASE_URL`、`DATA_DIR`、`LOCAL_STORAGE_DIR`；确认都指向恢复环境。
6. 执行 `npm run db:migrate`，然后在开放网页和 worker **之前**执行 `npm run replay-deletions`。
7. 运行健康检查；用两套账号确认未删除记录可回放、已删除记录返回 404、账号删除仍生效。
8. 验证题库版本、进度和用量，确认成功后再切换入口。

`replay-deletions` 会重复清理日志标记的会话或账号，是有意执行的删除动作，运行前必须确认恢复数据库和存储配置。脚本发现坏 JSON 或无效删除记录时退出，不会假装重放成功。

手动 Docker 流程还必须撤销备份中的登录会话与未使用邀请码，处理中面试需改为中断，并核对后来发生的密码变更和费用。上述步骤并未提供已经验收的 Docker 一键恢复命令；完成这些检查之前不能开放恢复实例供用户访问。

2026-10-09 已完成 Windows 本机实际 `pg_dump/pg_restore`：独立数据库中的录音、反馈、观点、词汇、复习与加密个人 Key 恢复验证；较旧备份之后的会话/账号/观点/词汇删除重放；拒绝原库、非空库、现有目录、损坏或缺失日志、文件篡改和越界路径。另把当前应用的一份真实本机备份恢复到临时独立库，核对内容与源库未改变，演练结束移除该临时库。详细证据仅在被 Git 忽略的 `data/verification/`。

可重复的恢复上线演练：

```powershell
npm run build
npm run check:recovery
```

命令仅使用新建的测试数据库和合成数据，端口为 5553 / 3101，全部 AI 与语音使用模拟服务。它实际执行完整备份、较旧快照恢复与新删除重放，启动 Next.js 和 worker，验证新登录、旧会话失效、私有音频与 Range 回放、报告、观点/词汇/复习、学习页面响应，以及恢复后的新观点与新录音处理。还验证已缓存连接与登录时，未完成恢复仍返回 503。报告写入独立 `data/verification/recovery-*/acceptance.json`，演练结束停止它自己启动的服务和测试数据库，不改变业务实例。

## 升级与回滚

1. 后台暂停新会话，等待正在录音的会话结束；停止 worker，确认备份完成。
2. 为新版本构建新的 `APP_IMAGE_TAG`，保留旧镜像。升级数据库前保留可恢复快照。
3. 启动 setup，迁移成功后启动 web / worker，再执行一次登录、录音、报告冒烟测试。
4. 若只是应用问题且数据库兼容，切回旧镜像。若迁移不兼容，先按上述流程恢复到独立库、重放删除日志，再切回旧版本。
5. 未确认新库可恢复前，不删除旧卷、不执行清空数据库命令、不手工修改迁移历史来掩盖失败。

恢复期间停止后台清理及录音写入，防止恢复出的对象和正在写入的对象相互覆盖。
